# MVP is a local CLI with no CI integration or skills installer

The MVP ships the rule format, a JSON source, the CLI (`check`, `explain`, `where`, `context`, file import), two skills installed by hand, and one install channel: npm. GitHub and GitLab integrations (Action, CI component, SARIF and `github` reporters, workflow generated by `init`), the `rulelink skills` installer, the managed `AGENTS.md` section, the shell and PowerShell installers and the Docker image move to V1 or V2.

The project is run by one person next to other work, and the MVP's exit criterion is that three external developers reach a first clean `check` in under 15 minutes. Each deliverable removed is one less thing to build, mirror and keep working across platforms. A developer who wants `check` in CI writes a workflow that runs `rulelink check`; the exit criterion still requires one such run.

## Considered options

- Full MVP as first drafted (two CI deliverables, four reporters, three installers, Docker, skills installer): rejected, too wide for the available time.
- Keep the Action and SARIF, cut only the GitLab component and Docker: rejected, the Action is itself a maintained deliverable with a mirror repository.

## Consequences

- `check --changed` is not in the MVP: `check` always checks and reports the whole project, and the consultation skill runs it as is.
- `annotate` is not part of the product: people and agents write the `@rule` comment themselves.
- `cargo install` is not an MVP install channel.
- The `sarif` and `github` reporters wait for the GitHub Action (V2).
- Release pipeline in the MVP: GitHub release archives and the npm package, built by dist (`.github/workflows/release.yml`).
- Amended by [ADR-0004](0004-shell-and-powershell-installers.md): the shell and PowerShell installers ship in the MVP too.
